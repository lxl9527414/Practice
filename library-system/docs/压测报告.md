# 云阁图书借阅系统 · 压测报告

> 测试时间：2026-10-13
> 被测版本：`library-system`（含借阅规则、预约排队、操作日志）
> 测试性质：**只读压测**，全程不写业务数据

---

## 1. 测试目标

1. 摸清单机混部部署下，核心读接口的容量上限（QPS）与延迟分布（P95 / P99）
2. 定位吞吐拐点，判断瓶颈在 CPU、数据库、磁盘 IO 还是连接池
3. 对比「服务端处理耗时」与「公网端到端耗时」，确认用户感知的慢点在哪一层
4. 产出可复现的测试方法，作为后续优化的基线

## 3. 测试工具与选择理由

### 3.1 为什么没用 ab / wrk / JMeter

服务器（CentOS 7）上排查结果：

| 工具 | 服务器可用性 |
| --- | --- |
| ab / wrk / hey / k6 / siege | 未安装 |
| Node.js | 已安装但**不可用**（`glibc` 版本过低，二进制启动失败） |
| Python 3.6.8 | 可用 ✅ |

为了不改动生产环境、不额外安装软件，最终用 **Python 标准库自写压测脚本**：

- `http.client`：HTTP/1.1 **keep-alive 连接复用**，避免把 TCP 握手算进延迟
- `threading`：按指定并发数启动工作线程，在时间窗口内循环发压
- `--duration` 控制每个场景时长，`--levels` 指定并发梯度，`--paths` 指定接口
- 输出指标：请求总数、QPS、平均延迟、P50 / P90 / P95 / P99、最大值、错误明细

脚本位置：`docs/loadtest.py`（零第三方依赖，可直接复制到任意有 Python 3 的机器运行）

### 3.2 使用方式

```bash
# 1. 获取管理员 Token（也可以是任意读者账号）
TOKEN=$(curl -s -X POST http://127.0.0.1:18080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<密码>"}' \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

# 2. 执行压测（预热 3 秒 + 3 个接口 × 3 档并发 × 15 秒）
PYTHONIOENCODING=utf-8 python3 docs/loadtest.py \
  --token "$TOKEN" \
  --paths "/api/books?current=1&size=10,/api/borrows?current=1&size=10,/api/dashboard" \
  --levels 10,25,50 \
  --duration 15

# 3. 同时观察系统资源
vmstat 5 60 > /tmp/vmstat.log
```

## 4. 测试设计

| 维度 | 设计 |
| --- | --- |
| 被测接口 | `GET /api/books`（图书列表分页）、`GET /api/borrows`（借阅记录，多表 XML 查询）、`GET /api/dashboard`（工作台 6 项聚合统计） |
| 并发梯度 | 1（预热）、10、25、50 |
| 单场景时长 | 预热 3 秒，正式场景各 15 秒 |
| 请求方式 | 仅 GET，只读，不带任何写操作 |
| 鉴权 | `Authorization: Bearer <token>`，Token 从 Redis 校验 |
| 资源采样 | 压测期间 `vmstat` 每 5 秒采样一次 |

**测试局限（如实说明）**：

1. 压测客户端与服务端**同机**，两者抢同一块 CPU，结果比独立压测机**偏保守**
2. 绕过 Cloudflare，测的是「应用 + 数据库」的服务端能力，不含公网链路
3. 只做 15 秒短时压测，未做长时间稳定性 / 内存泄漏测试
4. 单机单实例，不涉及集群与多副本场景

## 6. 瓶颈分析

1. **CPU 是硬瓶颈**：2 核被应用、MySQL、Redis、压测客户端共同占用，压测期间用户态 CPU 稳定在 92% ~ 95%，运行队列最高 19
2. **吞吐拐点在并发 10**：并发从 10 提到 50，QPS 只提升约 11%，而 P99 从 226 ms 涨到 688 ms —— 典型的排队效应，继续加并发没有收益
3. **连接池上限 10 与 2 核匹配**：Hikari 最大连接 10，MySQL 侧观察到的最大连接数正好是 11，说明请求在池外排队
4. **数据库与磁盘无压力**：慢查询 0、IO 等待 0、无 swap
5. **工作台接口最贵**：一次请求要执行 6 个聚合统计查询，QPS 只有图书列表的一半左右，是**最值得缓存**的接口
6. **端到端慢的根因在网络**：服务端 30 ~ 60 ms，公网 P95 1487 ms

## 7. 结论

- 在「2 核 1.76G 单机混部」这套配置下，系统可稳定支撑 **80 ~ 100 QPS 的读请求**（并发 10 的工作点），P99 控制在 350 ms 以内，零错误
- 极限吞吐约 **110 QPS**，再往上加并发只会堆积延迟，不会提升吞吐
- 扩容方向应当是 **加 CPU 核数** 或 **把 MySQL 拆到独立实例**，而不是调大连接池或加索引
- 用户侧真正感知的 1 秒延迟主要来自跨境回源链路，属于部署拓扑问题，不是代码问题

## 8. 优化建议（按性价比排序）

| 优先级 | 措施 | 预期收益 |
| --- | --- | --- |
| P0 | 工作台统计结果写入 Redis，TTL 30 秒 | 最贵接口 QPS 提升数倍，P99 明显下降 |
| P0 | 源站直连（DNS 改灰云 + Let's Encrypt 证书）或更换回源线路 | 端到端从 ~1.1 s 降到百毫秒级 |
| P1 | 前端 Element Plus 改按需引入 + 静态资源 gzip | 首屏 JS 从 1.2 MB 降到约 400 KB |
| P1 | 为 `book(updated_at)` 增加索引，列表分页减少排序开销 | 数据量增长后收益明显 |
| P2 | 升级到 4 核，或将 MySQL 拆到独立实例 | 吞吐上限约翻倍 |
| P2 | 引入 JMeter/wrk 做长稳压测与阶梯加压 | 覆盖内存泄漏、长时间稳定性 |

## 9. 数据可用于简历的表述

> - 压测与性能定位：在 2C2G 单机（应用 / MySQL / Redis 混部）用自研并发脚本压测核心读接口，10 并发下 83~99 QPS、P99 < 230 ms，50 并发吞吐饱和在 ~90 QPS，全程 11,275 请求 0 失败；结合 `vmstat`、慢查询日志定位瓶颈为 CPU 饱和，而非数据库或磁盘 IO。
>
> - 端到端性能分析：对比服务端单请求 30~60 ms 与公网 P95 1.5 s，定位耗时主要在 Cloudflare 跨境回源链路，据此提出源站直连与缓存优化方案。
